# 정렬 평가셋

파이프라인을 고칠 때마다 "좋아졌나" 를 눈이 아니라 숫자로 답하기 위한 것이다. 82 곡을
같은 방식으로 재고, 바꾸기 전후를 견준다.

이 자료는 두 번 사라졌다 — 한 번은 수집 자산을 지울 때, 한 번은 인스턴스를 파기할 때.
매번 다시 만드는 데 GPU 시간이 한 시간씩 들었고, 무엇보다 **이전 측정과 견줄 수 없게** 됐다.
그래서 저장소가 들고 있는다.

| 파일 | 내용 |
|---|---|
| `songs.json` | 곡 목록 — `video_id`, 아티스트, 제목, 언어, 가사 낱말 수 |
| `baseline.jsonl` | 2026-08-26 측정값. 곡마다 한 줄 |
| `results/` | 그날 네 갈래로 나눠 돌린 원본 결과 |
| `run.py` | 재는 하네스 |
| `cache_hearing.py` | 곡마다 여덟 벌을 듣고 캐시에 담는다. **GPU 를 쓴다** |
| `sweep.py` | 그 캐시로 설계 질문에 답한다. **GPU 를 쓰지 않아 즉시 끝난다** |
| `adaptive.py` | 곡마다 몇 벌을 들을지 골라도 되는가 |
| `watch.py`, `corpus_build.py`, `progress.sh` | 캐시 만들기와 진행 보기 |

## 듣기 캐시로 묻는 것

`cache_hearing.py` 가 한 번 들어 둔 것을 `sweep.py` 가 다르게 조합해 본다. 소리를 다시 듣지
않으므로 질문 하나가 몇 초에 끝난다 — 여덟 벌을 다시 듣는 데 곡당 139 초가 드는 것과 다르다.

```
cache_hearing.py --shard 0/8   →  hearing/<video_id>.json   (lyric, batches:{원본,영어,pitch±1,±2,slow,fast})
sweep.py <질문>                →  즉시
```

| 질문 | 답하는 것 |
|---|---|
| `order` | 합의가 자리를 준 낱말 중 시각순이 어긋난 것과 그 대가 |
| `agree` | 합의 문턱(`AGREE_SECONDS`)을 어디에 둘 것인가 |
| `leaveout` | 여덟 벌 중 어느 것이 보태고 어느 것이 깎는가 |
| `recipes` | 합의를 짓는 방식들을 나란히 |
| `gate` | 무엇을 검수로 보낼 것인가 |
| `korean` | 한국어가 뒤처지는 것이 영어 구절 탓인가 |

`sweep.py` 는 데몬을 직접 불러다 쓴다(`DAEMON` 상수). 연구용 사본이 아니라 출하하는 코드
그대로 재므로, 데몬을 고치면 여기 답도 같이 바뀐다. 경로는 그 기계에 맞게 고쳐야 한다.

`adaptive.py` 가 던지는 질문은 다르다 — **곡마다 몇 벌을 들을지 골라도 되는가.** 144 곡으로
재니, 원본 한 벌의 최장 빈 구간이 6 낱말 이하인 곡을 거기서 끝내도 빈 구간 8 이하인 곡 수는
108 로 같고, 합의가 도리어 망친 곡은 5 → 2 로 줄며, 여덟 벌을 다 듣는 곡이 144 → 80 이 된다.
그것이 데몬의 `HEAR_ENOUGH_GAP` 이다.

**가사 본문은 없다.** 저작물이라 저장소에 담지 않는다 — 관리 DB 에서 받아 온다.

## 재는 것

낱말 하나하나의 시각이 맞았는지는 사람이 들어야 알 수 있다. 그래서 대신 **몇 개나 실제로
들려서 자리를 잡았는지** 를 잰다. 자리를 못 잡은 낱말은 앞뒤 앵커 사이에 비례로 흩뿌려지는데,
그 값은 그럴듯해 보이지만 근거가 없고, 품질 점수에도 그럴듯하게 잡힌다.

| 열 | 뜻 |
|---|---|
| `anchors` | 받아쓴 소리에 실제로 맞물린 가사 낱말 수 |
| `gap` | 앵커 없이 이어진 가장 긴 낱말 수. 이 구간이 통째로 추측이다 |
| `breath.py` | 한 곡의 줄 경계가 숨 쉬는 자리에 떨어지는지 — `BREATH_FLOOR` 를 다시 놓을 때 쓴다 |

`anchors / words` 가 앵커 밀도다. 밀도와 최장 빈 구간은 서로 다른 것을 말한다 — 밀도가
높아도 한 군데가 통째로 비어 있을 수 있고, 사람이 어색함을 느끼는 것은 그 한 군데다.

`before` 는 원본을 한 번 받아쓴 것, `after` 는 피치·속도를 바꾼 여러 벌을 듣고 합의한 것이다.

## 2026-08-26 기준선

| 언어 | 곡 | 앵커 밀도 | 최장 빈 구간 | 빈 구간 8 이하인 곡 |
|---|---:|---|---|---|
| en | 32 | 86% → 92% | 11.1 → 4.8 | 20 → 26 |
| ja | 7 | 67% → 76% | 19.3 → 7.1 | 4 → 5 |
| **ko** | **40** | **64% → 73%** | **29.0 → 10.5** | **14 → 26** |
| und | 3 | 88% → 95% | 6.7 → 2.0 | 2 → 3 |
| 전체 | 82 | 73% → 81% | 20.4 → 7.7 | 40 → 60 |

한국어가 가장 약하다. 시작도 아래고, 여러 벌을 들려준 뒤에도 아래다.

여러 벌 듣기는 전체로는 크게 이기지만 **모든 곡에서 이기지는 않는다.** 이미 잘 맞던 곡
몇에서 최장 빈 구간이 도리어 늘었다 (Doja Cat "Agora Hills" 앵커 478→506 인데 빈 구간
7→13). 앵커가 늘면서 빈 구간도 느는 것은, 새로 온 낱말이 엉뚱한 시각에 놓여 순서가
어긋나고 뒤의 전역 정렬이 단조성을 지키려 멀쩡한 이웃을 버리기 때문으로 본다. 확인 중.

## 다시 재기

가사를 붙인 곡 목록을 먼저 만든다:

```
npx wrangler d1 execute mora-admin --remote --json --command \
  "SELECT r.artist, r.title, r.duration_ms, l.language, l.text, m.url
   FROM lyric_texts l
   JOIN input_revisions i ON i.id = l.input_revision_id
   JOIN recordings r ON r.id = i.recording_id
   JOIN media_sources m ON m.recording_id = r.id AND m.selected = 1
   WHERE l.layer != 'raw'" > dump.json
```

`video_id` 는 `m.url` 에서 뽑는다. 그 다음 GPU 마다 한 갈래씩:

```
python run.py --songs songs_with_text.json --shard 0/8
```

이미 끝난 `video_id` 는 건너뛰므로 중간에 끊겨도 이어서 돌리면 된다. 결과는
`results/shard<i>of<n>.jsonl` 에 곡이 끝날 때마다 즉시 쌓인다.

## 진짜 시각과 견주기 — LRCLIB 정답셋

2026-08-27 에 더했다. 그때까지 이 폴더가 재던 것은 전부 대리 지표였다 — 앵커 밀도, 숨 자리,
구절 수. 셋 다 "맞나"를 묻지 않고 "그럴듯한가"를 물었고, 그래서 "좋아졌나"에 매번 "아마도"로
답해야 했다.

LRCLIB 은 줄 단위 싱크 가사를 무인증 공개 API 로 준다. `songs.json` 82 곡을 물어보니 한국어
40 곡 중 18 곡에 싱크가 있었다(영어는 32 곡 중 29 곡). **낱말 단위는 한 곡도 없다** — 그래서
이 자로는 `line_spans` 만 잴 수 있고 `word_spans` 는 못 잰다.

| 파일 | 하는 일 |
|---|---|
| `truth.py` | LRCLIB 에서 줄 시각을 받아 `truth.json` 을 만든다 |
| `measure.py` | 그 곡들을 파이프라인에 통과시키고 우리 시각과 견준다 |

가사 본문은 저장소에 두지 않는다. 시각만 있으면 재는 데 충분하고, 글자는 `truth.py` 가 잴
때마다 다시 받는다.

가사 줄도 LRCLIB 것을 그대로 쓴다. 우리 가사 시트를 쓰면 두 시트의 줄을 짝지어야 하는데 —
줄 수가 다르고 머리글이 섞이고 후렴 반복이 어긋난다 — 그 짝짓기의 오류가 정렬의 오류와 섞인다.

자의 한계를 먼저 적는다. LRC 는 사람이 손으로 찍은 것이라 그 자체가 ±수백 ms 흔들린다. 믿을
수 있는 것은 **곡 사이의 견줌**이지 절대 정확도가 아니다.

### 이 표를 읽을 때 — 절반은 로마자였다

위 표를 낸 다음 날 글자 구성을 세어 보고서야 알았다. **LRCLIB 의 한국어 항목 여덟 곡은 한글
원문이 아니라 로마자 표기였다.** 「WOODZ - Drowning」은 한글 0 자에 라틴 931 자다. 그 여덟
곡에는 로마자 가사를 먹여 놓고 "아이돌과 랩을 못 알아듣는다"고 읽었다.

제품은 멜론·지니에서 한글 원문을 받는다. 그러니 그 여덟 곡의 실패는 파이프라인의 성질이
아니라 이 평가셋의 결함이다.

| 가사 | 곡 | 오차 가운뎃값 | 밀도 가운뎃값 |
|---|---|---|---|
| 원문 또는 실제 영어 | 9 | 440ms | 0.86 |
| 로마자 | 8 | 1230ms | 0.51 |

걸러내고 보면 남는 것은 둘이다.

**한국어 원문 다섯 곡은 전부 좋다** — 114·162·175·244·440ms. 이 파이프라인은 한글 시트에
대해서는 제 일을 한다.

**일본어 세 곡은 원문인데도 전부 나쁘다** — 0.07·0.00·0.35. 로마자 핑계가 통하지 않는
자리이고, 여기가 실제로 고칠 곳이다. 그중 「IRIS OUT」의 밀도 0.00 은 written_language 가
가나·한자를 세지 않아 영어 모델을 고른 탓이었다(2026-08-27 고침). 나머지 둘은 언어를 바로
골랐는데도 나쁘므로 다른 원인이 더 있다.

**앵커 밀도 0.7 이 좋은 것과 나쁜 것을 정확히 가른다.** 통과한 여섯 곡은 114~822ms, 막힌
열한 곡은 976~5464ms 로 겹치는 곡이 하나도 없다. 품질 게이트의 문턱은 실측으로 옳다.

그러니 이 파이프라인은 고장난 것이 아니다. **되는 곡에서는 210ms(가운뎃값)로 된다.** 문제는
정확도가 아니라 적용률이다 — 열일곱 곡 중 열한 곡을 처리하지 못한다.

무너지는 곡에 결이 있어 보이지만 — 발라드는 통과하고 아이돌·랩·일본어가 막힌다 — 위에 적었듯
아이돌과 랩 쪽은 로마자 가사였다. 자료를 걸러내면 남는 결은 **일본어**뿐이다.

다음에 이 평가셋을 쓸 때는 로마자 여덟 곡을 빼고 재야 한다. truth.py 는 아직 그것을 가려내지
않는다 — 한글·가나 비율로 거를 수 있고, 그 전까지는 이 표의 아래 절반을 근거로 삼지 말 것.
